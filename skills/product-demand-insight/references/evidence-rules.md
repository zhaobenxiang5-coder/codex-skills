## 1. 证据记录

每条来源至少保留：

| 字段 | 说明 |
|---|---|
| `id` | 稳定且唯一的证据 ID |
| `sourceType` | review、qa、trend、search、competitor、interview、return、internal 等 |
| `platform` | 平台、站点或内部系统 |
| `urlOrFile` | 可回查的 URL 或绝对文件路径 |
| `title` | 页面、帖子、文件或数据集标题 |
| `capturedAt` | 采集时间 |
| `market` | 国家、语言或站点 |
| `originalTextOrMetric` | 原文、原始数值或其定位信息 |
| `provenanceLevel` | 项目已有等级；没有时写 `unclassified` |
| `freshness` | current、aging、stale 或 unknown |

不要编造 URL、评论、销量、时间或证据 ID。截图只能证明截图中可见内容；页面摘要不能替代商品详情或评论原文。

## 2. 结论类型

### `fact`

来源直接支持的结论。必须有 `evidenceRefs`，表述范围不得超过来源。

示例：三条已核验评论都提到扣具单手难解。

### `inference`

从多条事实合理推导的解释。必须同时写出依据、置信度和可能反例。

示例：通勤遛狗用户可能更在意单手操作，因为评论集中发生在牵绳场景。

### `hypothesis`

待验证的用户、动机、结构或商业判断。允许没有直接证据，但必须进入 `missingEvidenceTasks` 或验证计划。

示例：身份认同可能来自“专业训犬”视觉，而不是单纯颜色偏好。

## 3. 需求证据通道

在 `flow-task-center-pro` 中，正式需求至少要闭合四条通道：

1. **趋势速度 / why now**：证明近期变化，而不是静态热卖。
2. **评论痛点 / unmet need**：证明买家真实抱怨、追问、退货或反复描述。
3. **平台表达差 / gap**：证明跨来源存在同一需求，但当前商品表达或承接不足。
4. **结构化需求上下文**：明确谁、场景、痛点、why now，并保留原始词。

榜单、sold、rank、供应商销量和 AI 总结不能单独替代以上任一通道。

## 4. 证据强弱

项目存在正式证据等级时，直接使用项目定义，不自行重写。没有正式等级时，按以下原则做人工判断：

- **强**：当前可回查的原始数据、直接评论/问答、内部退货或成交事实、多来源一致证据。
- **中**：可回查页面、单一平台结构化样本、完整访谈记录。
- **弱**：页面摘要、单条无上下文内容、二手转述、供应商营销文案。
- **非证据**：模型常识、为了让报告完整而补出的数字或故事。

证据数量不能替代证据质量。重复转载或同一数据源的多个镜像只算一条来源。

## 5. 闸口判定

| 状态 | 使用条件 |
|---|---|
| `hypothesis-only` | 没有可回查证据，或输入仅为产品想法/商品名 |
| `evidence-needed` | 有真实证据，但缺趋势、评论、场景、反证或新鲜度 |
| `manual-review` | 证据已形成开发方向，但没有外部正式闸口或人工确认 |
| `ready-for-domestic-sourcing` | 外部正式闸口通过、阻断为空、人工已确认 |

不能用模型评分代替外部闸口。无法确认外部闸口时，停在 `manual-review`。

需求阶段只允许形成需求实体、证据任务和开发简报。正式商品事实必须来自后续供应商详情、SKU、样品和人工确认。

## 6. 常见错误

- 把“有画面感”当真实性。
- 根据一个产品名生成四类用户，再称其为已验证画像。
- 把痒点或爽点写成买家明确表达过的事实。
- 把低/中/高成本判断当目标成本。
- 让营销卖点反向污染材质、尺寸、认证或功能事实。
- 用 1688 商品词证明海外需求。
- 用搜索结果摘要代替评论和详情。
- 在缺少包装尺寸、重量和采购价时宣称直发利润成立。
- 在需求分析完成后直接进入生图、Listing 或发布。
